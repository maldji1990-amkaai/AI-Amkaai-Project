# AmkaAI — Wan 2.2 TI2V-5B RunPod Pod server

This is the missing GPU-side service for the existing AmkaAI `runpod-pod-manager.ts`.

It implements the exact contract already expected by the web application:

- `GET /health`
- `POST /generate` → `{ "id": "provider-job-id" }`
- `POST /cancel/:id`
- `GET /status/:id`

The server loads the official `Wan-AI/Wan2.2-TI2V-5B` model and keeps it resident for the lifetime of the Pod. The model weights are downloaded into `/workspace/models`, so a RunPod network volume can be used to avoid downloading the ~34 GB model again on every new Pod.

## Important storage choice

The model repository is about 34.2 GB. Use a **RunPod network volume of at least 60 GB** (80 GB is safer) mounted at `/workspace`.

The existing AmkaAI manager is patched to accept:

```env
RUNPOD_NETWORK_VOLUME_ID=...
```

If this is set, the manager attaches that network volume to each new Pod.

## Result storage

The existing AmkaAI manager terminates the Pod after the queue becomes idle. Therefore a video URL must not point to the Pod itself.

This server uploads completed MP4 files to Cloudinary before sending the completion webhook. The same Cloudinary account already used by the web application can be used.

Required inside the RunPod Pod:

```env
CLOUDINARY_CLOUD=...
CLOUDINARY_API_KEY=...
CLOUDINARY_API_SECRET=...
CLOUDINARY_VIDEO_FOLDER=amkaai/videos
```

Do not put these secrets in GitHub.

## Build

From this directory:

```bash
docker build -t amkaai-wan22:1.0.0 .
```

Push the image to a registry that RunPod can access, for example GHCR, then configure:

```env
RUNPOD_POD_IMAGE=ghcr.io/YOUR_ACCOUNT/amkaai-wan22:1.0.0
```

You can also create a RunPod template from this image and use:

```env
RUNPOD_POD_TEMPLATE_ID=...
```

The template and image are alternatives; the manager prefers `RUNPOD_POD_TEMPLATE_ID` when both are present.

## Recommended runtime variables

```env
WAN_MODEL_ID=Wan-AI/Wan2.2-TI2V-5B
WAN_WIDTH=1280
WAN_HEIGHT=704
WAN_FRAME_NUM=121
WAN_SAMPLING_STEPS=40
WAN_GUIDE_SCALE=5.0
WAN_SHIFT=5.0
WAN_OFFLOAD_MODEL=true
WAN_T5_CPU=true
WAN_CONVERT_MODEL_DTYPE=true
WAN_MAX_QUEUE=8
```

The official Wan2.2 documentation states that TI2V-5B supports 720p and can run on a GPU with at least 24 GB VRAM such as an RTX 4090. It uses the 1280×704 or 704×1280 720p shapes.

## First test

After the Pod starts:

```bash
curl http://127.0.0.1:8000/health
```

It should return HTTP 200 only after the model has downloaded and loaded.

Then test:

```bash
curl -X POST http://127.0.0.1:8000/generate \
  -H "Content-Type: application/json" \
  -d '{
    "job_id":"manual-test-1",
    "webhook_url":"https://example.com/webhook",
    "prompt":"A cinematic aerial shot of a futuristic city at sunset",
    "duration_seconds":5,
    "clip_length_seconds":5,
    "clip_count":1,
    "model":"Wan2.2-TI2V-5B"
  }'
```

For the real AmkaAI path, the webhook URL is generated by `lib/video-dispatch.ts`, so you do not need to hard-code it.

## Notes

- The current AmkaAI pricing layer sends 5-second clips. The server supports multiple clips and concatenates them with FFmpeg before upload.
- Cancellation stops additional clips. If a diffusion pass is already running, the current pass cannot be safely interrupted without risking CUDA/model state.
- The first Pod start can be much slower because the model must be downloaded and loaded.
- The Docker image intentionally does not bake the 34 GB weights into the image. Keeping weights on the RunPod network volume makes image builds and Pod creation much smaller.
- The official Wan repository includes `flash_attn` in its dependency list but also contains an SDPA fallback. This first patch deliberately avoids a fragile CUDA-specific flash-attention build. Once the first end-to-end generation is confirmed, flash-attention can be added as a performance optimization if needed.
